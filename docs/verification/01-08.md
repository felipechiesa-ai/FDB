# 01-08 verification

Status: `[NOT COMPLETE]`. Backup and restore are implemented and tested on real folders. The Library menu has not been checked on screen, so the acceptance check is open.

## Implementation

Restore follows the charter procedure, recorded in [decision 0002](../decisions/0002-restore-procedure.md):

1. Validate the backup (manifest, format version, snapshot checksum, integrity and foreign-key checks, known migrations, original checksums).
2. Stage a copy in a `Restoring-<timestamp>-<id>` folder beside the library, open it, and check its originals and integrity. A failure removes the staging folder.
3. Write a recovery backup of the current library.
4. Release the active database (the app swaps in an empty in-memory store), write `restore-in-progress.json`, move the active library to `Recovery/Replaced-…`, and move the staged library into place.
5. Reopen and remove the marker. If the restored library does not open, move it to `Recovery/Failed-Restore-…` and put the previous library back.
6. At launch, an interrupted swap is settled before the library opens.

While the swap runs, a busy overlay blocks editing. If neither library opens, the overlay stays until the app is quit and reopened.

## Not verified

- The Library menu on screen: the backup folder picker, the restore folder picker, the confirmation dialog, the busy overlay, the success message, and the blocked overlay.
- A restore followed by quitting and reopening the app. The launch recovery is tested with real folders, but not through a real quit during a swap.
- A backup restored on a second Mac.
- Disk use of the `Recovery` folder after repeated restores. Each restore keeps a replaced library and a recovery backup; cleanup is not implemented.

## Limitations

- A restore cannot be cancelled once staging starts. Cancelling at the confirmation dialog changes nothing.
- No progress is shown for large backups or restores. The restore overlay is the only busy indicator.
